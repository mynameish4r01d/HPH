# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A static, hand-written HTML/CSS/JS marketing site with no build system, no package manager, and no test suite. There is no `package.json`, no bundler, no framework. Every page is a plain `.html` file paired with its own `styles.css`, linked directly via `<link>`/`<script>` tags.

## Running it locally

There is no dev server or build step. Open the HTML files directly in a browser, or serve the directory with any static file server, e.g.:

```
python3 -m http.server 8000
```

Then navigate to `http://localhost:8000/index.html`.

## Site structure

The repo root is a landing page (`index.html`, `app.js`, `styles.css`) that links out to two independent sub-sites, each a self-contained mini-site with its own home/about/etc. pages:

- `HPH TECHNICAL SOLUTIONS/` — pages: `home`, `about`, `milestones`
- `HPH RENEWABLE/` — pages: `home`, `about`, `products/product-pages/content1/page1|2|3` and `content2/page1|2` (individual product pages only — there is no all-products listing page; the product lineup is reached through the nav menu), `contact`, `legal-policies` (`terms-and-conditions`, `privacy-policy`, `return-and-refund-policy`)

Each page is a directory containing `index.html` + `styles.css`, and often an `elements/` subfolder holding page-local images/videos referenced by relative path.

**JS sharing is inconsistent between the two sub-sites** — don't assume one pattern applies to both:
- `HPH RENEWABLE` has its own copy of `app.js` (`HPH RENEWABLE/app.js`) that its pages reference via `../app.js`.
- `HPH TECHNICAL SOLUTIONS` has no local `app.js`; its pages reach up to the repo-root `app.js` via `../../app.js`.

Global asset folder naming also differs between sub-sites (not a typo to "fix" without checking both):
- `HPH RENEWABLE/global-elements/` (hyphenated)
- `HPH TECHNICAL SOLUTIONS/global elements/` (space)
- repo root: `global elements/` (space)

When adding a new page inside a sub-site, match that sub-site's existing relative-path depth and JS/asset-folder convention rather than copying from the other sub-site.

## Shared front-end patterns

`app.js` (and `HPH RENEWABLE/app.js`, kept in sync manually) provides the same behavior across all pages:

- **Scroll-reveal animation**: elements with class `hidden` are observed via `IntersectionObserver`; `show` is toggled on/off as they enter/leave the viewport. The corresponding CSS (`.hidden`/`.show` in each page's `styles.css`, derived from the root `styles.css`) defines the blur/translate/opacity transition. Siblings under a `.logo` container get staggered `transition-delay` via `:nth-child` for a cascading reveal effect.
- **Image slider**: `showSlides()` / `plusSlides()` / `currentSlide()` drive a manual slideshow over elements with class `mySlides` and dot indicators with class `dot`.
- **Hamburger/dropdown menu**: `toggleMenu()` toggles a `.menu a` active state and a `header.black` class; wired up via a listener on `.menu` and the first `.dropdown` element. Note this listener setup assumes both elements exist in the DOM — pages without a `.menu`/`.dropdown` element will throw on load if `app.js` is included unmodified.

**Desktop/mobile split**: layout is done via two top-level containers per page, `<div class="desktop">...</div>` and `<div class="mobile">...</div>`, toggled by a `@media (max-width: 750px)` query in each page's `styles.css` (desktop hidden, mobile shown below that width). **The `.mobile` containers are currently empty placeholders across every page in the repo** — mobile layouts have not been built out yet. Don't assume mobile support exists when making changes; flag it if a task depends on it.

CSS uses native nested selectors (e.g. `.desktop { .content { .text-container { ... } } }` in `styles.css`) rather than a preprocessor — there is no Sass/Less build step, so this relies on browser-native CSS nesting support.

## "Schedule a Visit" form (HPH RENEWABLE, Firebase)

Every "Schedule a Visit" link on HPH RENEWABLE points to the dedicated page `HPH RENEWABLE/schedule-a-visit/` (same tab). Product pages append `?product=<name>`, which pre-ticks the matching interest (`INTEREST_BY_PRODUCT` in `visit-form.js`: MX2250 → Micro Inverter, the MSU/MAU/B units → Battery). Instead of a product, visitors pick what they're interested in with two tick-chips (`.visit-chip`, checkboxes named `interest`): Solar, Battery, or both. The Solar chip still saves as "Micro Inverter". This is saved in the existing `product` field as "Micro Inverter", "Battery", "Micro Inverter + Battery", or "Not sure yet" when neither is ticked. The admin page labels it "Interested in", and older requests keep the product they named. The form there is one shared block (`<main class="visit-page">`, outside `.desktop`/`.mobile`, like the FAQ page) handled by `schedule-a-visit/visit-form.js` (ES module). The form is three screens on one page (`.visit-panel`, `data-step` 1–3, `showStep()`), with a step indicator on top (`.visit-steps`) and Back / Next below (`.visit-nav`):
1. **Your details:** every field from name to message, including the aircons.
2. **Electricity bill:** the bill upload.
3. **Roof location:** the roof screenshot, the consent box and "Request a Visit" (`.visit-send`).

How the steps behave:
- **Checks:** Next checks that screen's fields first, and Enter in a field means Next until the last screen.
- **Optional uploads:** Next reads "Skip for now" while a screen's upload is empty.
- **Moving between screens:** each screen scrolls back to the top of the page, so the heading and indicator aren't hidden under the fixed nav.
- **Sending:** sending checks everything again and jumps back to the screen with any problem.
- **Data:** nothing about the saved data changed. Answers go to Firestore collection `visitRequests`; optional attachments (≤3 images/PDFs, 10 MB each) go to Cloud Storage under `visitRequests/<request id>/`. The upload field asks for the visitor's latest electricity bill (with the "Your Monthly Consumption" graph visible), which is used to estimate usage for an accurate quote, and it is marked "recommended", not required. It still accepts up to 3 files, in case the bill has several pages. `visit-form.js` keeps its own `chosenFiles` list, so each pick adds files instead of replacing the last pick, and each file has a remove button. Files can also be dragged onto the upload box. Picked and dropped files both go through `addFiles()`, and drops elsewhere on the page are ignored so the browser doesn't navigate away. The box shows drag-and-drop wording on mouse devices and "Tap to add…" on touch devices (`@media (hover: none)`). JPEG/PNG/WebP photos over 2 MB are shrunk in the browser to a JPEG with a 2400px long edge before upload. When the browser reports no file type (e.g. HEIC on Windows), the type comes from the file extension, which keeps uploads within `/storage.rules`, and their paths are stored in the request's `attachments` field. A "When do you use the most electricity?" dropdown is saved as `usagePattern`: Balanced (called Flat before; the rules still accept "Flat", and the admin page shows older ones as Balanced; Evening Peak is no longer offered, but older requests keep it and the rules still accept it), Mostly Day, Middle of Day, Mostly Night, or blank for "Not sure". It's optional in the rules (`isUsagePattern()`), so a cached older form still submits. The admin page shows it as "Usage pattern" in the details, the CSV and Edit details (`EDIT_FIELDS`), so keep the list in step in all three places. **Address suggestions (Google Places):**
- **Suggestions:** as visitors type their property address, Google suggests places in the Philippines. These come from Places API (New), through `AutocompleteSuggestion.fetchAutocompleteSuggestions` and `.visit-address-suggest`, with "Powered by Google" shown under the list. Arrow keys and Enter work in the list.
- **Picking one:** it fills the box with Google's formatted address and saves `addressPlace` (`{ id, lat, lng }`). Typing over it afterwards forgets the place.
- **The key:** it lives in `HPH RENEWABLE/maps-config.js` (`GOOGLE_MAPS_API_KEY`). It's restricted to the site's domain and to the Maps JavaScript API and Places API (New), with billing on in the Google Cloud project. While it starts with `YOUR_`, the box is a plain text field.
- **Admin page:** the Ocular Visits address links to Google Maps directions (`directionsUrl()`). It goes to the exact place when there's an `addressPlace`, else to the typed address, and it opens the Maps app on phones. Changing the address in Edit details removes the old `addressPlace`.
- **Rules:** `isAddressPlace()` checks the place, and it's optional in `isValidVisitRequest`/`isValidStaffVisit`/`isValidVisitEdit`.
- **Testing:** tested against the emulator, and in Chrome with a stand-in for Google's library.

Two more optional fields help the quote:
- **Aircons:** "How many aircons do you use?" is a −/+ stepper (0–10, `MAX_AIRCONS`), then one capacity dropdown per aircon (`AIRCON_SIZES`: Not sure, 0.5–3 HP). Each row's choice is remembered if the count goes down and up again. It's saved as `aircons`, a list such as `["1 HP", "1 HP", "1.5 HP"]`, and left out when 0. The rules check it with `isAirconList()`, so keep the sizes in step there.
- **Roof screenshot:** "Pinned location of your roof (recommended)", the third screen, takes up to 2 images (a Google Maps screenshot with the roof pinned). They upload to `visitRequests/<id>/roof-…` and are saved as `roofPhotos`.
- **Uploaders:** both upload boxes use `makeUploader()` in `visit-form.js`.
- **Admin page:** it shows "Aircons" as e.g. "3 aircons: 2 × 1 HP, 1 × 1.5 HP" (`airconSummary()`, also a CSV column), and the roof screenshots in their own "Roof location" section (also counted in the paperclip and a "Roof screenshots" CSV column). They're deleted with the request.
- **Rules and editing:** both fields are optional in `isValidVisitRequest`/`isValidStaffVisit`, and Edit details leaves them unchanged. They were tested against the emulator (10 requests).

An optional "Referral code" field (pre-filled from `?ref=<code>`) is saved as `referralCode`; it's optional in `isValidVisitRequest` too, so a cached older form still submits. Codes come from the sales team list in `HPH RENEWABLE/referral-codes.js` (`SALES_TEAM`, `findReferrer()`), shared by the form and the admin page, so a new salesperson is one line there. Matching ignores case, spaces and dashes, and the official spelling is saved. A valid code shows "✓ Referred by <name>". A wrong one shows "That referral code doesn't exist" when the field is left, and blocks submitting. Blank is fine. The check is in the form only, not the rules. The admin page shows the salesperson's name with the code everywhere: the entry, the referral leaderboard, the CSV "Referred by" column and search. Codes not on the list show as "Unknown code". Its Edit details form rejects a new unknown code but keeps an older one left unchanged. Firebase settings: `HPH RENEWABLE/firebase-config.js` (while `projectId` starts with `YOUR_`, submitting shows a call/email fallback message). The SDK loads from gstatic only on submit.

- Security rules: `/firestore.rules` and `/storage.rules` — the public may create validated requests/files only; no public reads, edits or deletes. If you add or rename a form field, update `visit-form.js` and the field list in `firestore.rules`, or every submission will be rejected; upload limits live in both `visit-form.js` and `storage.rules`.
- ES modules don't load over `file://` — test the form through a local server (`python3 -m http.server`).

## Name and address tidying (HPH RENEWABLE forms and admin)

`HPH RENEWABLE/text-format.js` (`tidyName`, `tidyAddress`, `tidyOnBlur`) tidies text typed in ALL CAPS or all lowercase, e.g. "harold t. hermosa" → "Harold T. Hermosa".
- **Where:** the Schedule a Visit and Join the Waitlist forms tidy name and address. Feedback tidies name, and the NDA form tidies `fullName`.
- **When:** each form tidies the field when the visitor leaves it, and again on submit.
- **Rules:**
  - Mixed-case words are kept (McDonald).
  - Hyphens and apostrophes are handled (Mary-Jane, O'Brien).
  - A Roman numeral stays in capitals as a name's last word (Rizal III) or anywhere in an address after the first word (Phase IV).
  - Ordinals stay lowercase (12th).
  - An address typed in normal mixed case keeps its all-caps words (BGC). One typed all in capitals is tidied throughout.
- **Admin page:** `tidyLoadedText()` (`TIDY_FIELDS` in `admin.js`) shows older entries tidied after loading: visits, waitlist, feedback, NDA and installs. Saved data only changes if someone saves an edit. Checklists are left as saved; their form tidies the name and address when saving. The admin edit and add form also tidies the name and address it saves.

## Inventory (HPH RENEWABLE admin, Firebase)

The installer workspace, the team workspace (encoder) and admins have an **Inventory** tab (`TABS.inventory` and the "inventory" section of `admin/admin.js`; `canKeepInventory()` in `/firestore.rules`, and the `inventory/` rule in `/storage.rules`). On that tab the installer's and encoder's home is "Stock on hand".
- **Items:** `inventory/{id}` holds `name`, `category`, `unit`, `qty`, `lowAt` (restock level, 0 = warn only when none are left), `note`, an optional `supplierId` (see "Suppliers" below), `photos` (up to `INV_MAX_PHOTOS`, 6, shrunk like other uploads, in Storage under `inventory/<id>/`, each with a small `thumb-<name>` JPEG copy, see below), `lastLogId` and `createdAt/By`, `updatedAt/By`. Category and unit are dropdowns. The categories (`INV_CATEGORIES`) are Cables & Wiring, Connectors, Major Equipment, Mounting & Racking and Grounding Hardware, and a category is required. The units (`INV_UNITS`) are pcs and mtrs. An older value not in the list stays selectable. An item is "Restock" (amber) at or below `lowAt` and "Out of stock" (red) at 0. The list sorts those first, and the sidebar's "Restock needed (n)" button filters to them. A category dropdown beside the search box filters by category (`.admin-category-filter`, `renderCategoryFilter()`, `activeCategory`). It lists All categories, the `INV_CATEGORIES`, any older category still in use and "No category" if any, each with a count. It combines with search and the restock filter, and Export CSV follows it. With All categories, the list is grouped by category (`groupedInventory()`), in the dropdown's order. Each group has a heading with its count and "n to restock", and the heading stays pinned while scrolling on desktop. Within a group the order is out of stock, then low, then by name.
- **Photo thumbnails:** each upload also saves a `thumb-<name>` copy beside it (`INV_THUMB_EDGE`, 320px long edge, `uploadThumb()`). The list, pane header, profile photo and edit form show it (`thumbUrl()`); only the full-size viewer loads the photo itself (`photoUrl()`). Both are uploaded with a year-long `cacheControl` (`INV_CACHE`), which is safe because paths are never reused. A photo with no thumbnail falls back to the full photo, and `backfillThumb()` makes one in the background for someone who can edit the inventory (one at a time; it uses `getBlob`, which needs CORS on the bucket, and stops for the session if that fails). `deletePhotos()` removes thumbnails with their photos. New photos are always saved as a JPEG of at most `INV_PHOTO_EDGE` (1600px, `shrinkItemPhoto()`), not the 2400px/2 MB rule the other uploads use. Older photos over 500 KB are swapped for such a copy by `shrinkOldPhotos()`, which runs in the background when an owner loads the page (like `fillMissingCapacities()`). Storage files can't be replaced, so it uploads a new file, swaps the path in the item's `photos` in a transaction (skipped if the photo was removed meanwhile), then deletes the old photo and thumbnail. Paths already checked are kept in localStorage (`hph-admin-photos-checked`). It changes the item's `updatedAt/By`. The `inventory/{itemId}/{fileName}` storage rule covers thumbnails as-is.
- **Changing the count:** each item has a stock panel: Use / Add stock / Set count, a −/+ stepper, a preview of the new count, "Used for" (client suggestions from Ocular Visits) and a note.
  - **Saving:** there's no save button. A change saves `PANEL_SAVE_MS` (1.5 s) after the last tap, with "Saving in a moment… Cancel" shown meanwhile.
  - **Text fields:** it waits while Used for / Note is being typed in, and saves when the field is left or Enter is pressed.
  - **Starting values:** Use and Add stock start at 0, so nothing saves until an amount is picked. Set count starts at the current count.
  - **Mode:** switching mode drops an unsaved change, and the mode is remembered per item (`panelModes`).

  `changeStock()` runs a transaction that updates the item and writes an `inventoryLog/{id}` record (`itemId`, `itemName`, `reason` create|use|restock|count, `change`, `qtyBefore`, `qtyAfter`, `job`, `note`, `at`, `by`), shown as the item's History. Each list row also has a quick − count + (`quickStepper()`). Taps are added up and saved as one Used / Stock added change `QUICK_SAVE_MS` (1.5 s) after the last tap (`saveQuick()`, same transaction and rules). The count shows blue until saved, and leaving the page saves what's waiting and asks to confirm. The add/edit form (`showItemForm()`/`itemForm()`) changes details and photos only; a new item's starting count is written with a "create" record.
- **Rules:** `isValidInventoryItem`, `isInventoryLogFor` and `isValidInventoryLog` in `/firestore.rules`. A count change must come with a new record for that item whose before/after match, and records can't be edited (admins may delete them). The installer and admins read and write. Admins delete any item, the installer and encoder only their own. Photos use the `inventory/` rule in `/storage.rules`. The history query filters by `itemId` only and sorts in the browser, so it needs no composite index.
- **System presets:** a "System presets" button in the Inventory sidebar (inventory editors; `.admin-presets`, `showPresets()`) opens a pane with a fold-up card per system (a `<details>` whose header shows the name, status and Use button; one open at a time, `openPreset`, kept through redraws): 2, 4, 6 and 8 kW (`INV_PRESETS`, the owner's parts lists; line keys and names in `PRESET_LINES`, MC4 connectors counted in sets, and the 8 kW's "MI Box (13 ways)" is a separate item from the "MI Box").
  - **Linking:** each line takes stock from one inventory item. It's the item whose name matches (`presetNorm()` ignores case, spacing, plurals, "Amp"/"A" and "w/"; exact first, else the only item containing the name, never another line's exact item), or the one picked in the line's dropdown. Picks are saved for everyone in Firestore `inventoryPresets/links` (`{ links: { <line key>: <item id> } }`, the `inventoryPresets` rule in `/firestore.rules`).
  - **Using one:** "Use <n> kW system" works only when every line is linked and in stock (lines on the same item add up). Otherwise the card shows what's not linked or short, and nothing changes. Each item then goes through `changeStock()` one at a time, so the History notes say "<n> kW system preset". If one fails part-way, what was taken is put back.
  - **Undo:** "Used just now" lists each use this visit with what it took and an Undo (adds it back, noted "Undo: …"). It lasts until the page is reloaded. Leaving the page mid-run asks to confirm, and the auto sign-out waits for it.
- **Suppliers:** Settings (click the profile) has an Inventory → Suppliers row for anyone who can see the inventory, with the number of suppliers. It opens supplier profiles (`showSuppliers()`, drawn into `.admin-settings-suppliers`; `supplierView` is the list, a profile or the add/edit form).
  - **Profiles:** Firestore `suppliers/{id}` holds `name` (unique, case ignored, checked in the page), `contactPerson`, `phone`, `email`, `address` (office or warehouse), `note`, `createdAt/By` and `updatedAt/By`. The rule is `isValidSupplier` in `/firestore.rules`: inventory viewers read, editors add and edit, Edit + delete deletes any, and Edit deletes only its own. Suppliers load with the page (`suppliers`), on their own like the wishlist.

## Live portfolio counters (HPH RENEWABLE)

`HPH RENEWABLE/portfolio-counters.js` (plain `defer` script) fills in the installed-count and total-capacity counters. It reads the totals from Firebase (`installCounts`, see "Installations / serial numbers" above) and falls back to the installation Google Sheet. It loads `firebase-config.js` relative to its own URL and uses a named Firebase app (`portfolio-counters`) so it doesn't clash with the admin page's app. It's loaded by `home/`, `portfolio/`, `our-advocacy/` and `admin/` (an "Installed portfolio" box under the Overview heading, with line dividers like the Home page) and finds its elements by data attributes — `data-portfolio-count="inverters|panels|inverter-capacity|solar-capacity"` (capacities also need `data-unit`), `data-portfolio-count="yearly-savings|lifetime-savings"` (installed MX2250s × `SAVINGS_PER_MX2250_YEAR`, ₱49,600, an estimate that may change, so keep it in sync with the FAQ and savings calculator), `data-portfolio-goal="inverters"` (progress toward `GOALS`, sets `--progress`), plus optional `data-portfolio-status-dot` / `-status-text` / `-error` — so any page can show them without its own copy of the logic. The per-unit ratings (2.25 kW per inverter, 0.65 kWp per panel) live at the top of that file. It requests only the serial-number columns with the gviz query `select F, H` (`COLUMNS_QUERY`), checks the returned headers, and falls back to the whole sheet if the columns have moved. It remembers the last counts in localStorage (`hph-portfolio-counts`) and shows them instantly on the next visit. It refreshes every 30 s without dimming the numbers, and on a failed refresh it keeps the last known numbers. Both pages preconnect to `docs.google.com`. Note: the sheet is readable by anyone with the link, including the client columns.

## Dark mode (HPH RENEWABLE)

Dark mode follows the visitor's system setting (`prefers-color-scheme`) on desktop and mobile. It uses the same #FFFFFF → #0C0C0C surface mapping everywhere, with #EBEBEB text, #9E9E9E muted text and #2A2A2A borders.
- **Product pages** (`products/product-pages/*`): the MX2250 page (`content1/page1`) is deliberately light only, because its photos aren't made for a dark page. It has no dark rules and carries `<meta name="color-scheme" content="light">`. The MSU4000 Elite, MAU5000 Elite, B4000 Elite and B5000 Elite pages have dark mode, at the owner's request (`content="light dark"`). Their dark rules are at the end of each `styles.css`: nav, page content, mobile tokens, the 3D slide's dark grey stage (#1C1C1E), dots, arrows, controls, labels, tour card, and (MSU/MAU) the steppers, total capsule and price line. The photo slides keep their light stage, because the charcoal products disappear on a dark background.
- **Home** has its own desktop dark block inside `.desktop`. Its landing text sits over the video and stays white.
- **Every other page** ends its `styles.css` with a `/* ===== DESKTOP DARK THEME ===== */` block for the desktop nav, mega panel and footer. Base colours there are nested deep, so these rules use `!important`, as Home's do. After it, depending on the page, comes one of the following:
  - the page's content dark tokens (sim pages, Our Advocacy, form pages, FAQ), copied out of the phone media query so they also apply on desktop. FAQ's are nested in `.faq-page` so they outweigh its desktop selectors.
  - a "Desktop page content (dark)" block (About, Mission, Contact, Portfolio, legal pages) that repeats each light content colour's selector with its dark counterpart, winning by coming later.
- When you add a coloured element to a page, add its dark counterpart too.

## Conventions to follow

- Each page's CSS lives in a `styles.css` next to its `index.html`; there is no shared/global stylesheet imported across pages beyond what's copy-pasted from the root `styles.css` patterns (`.hidden`/`.show`, desktop/mobile toggle, font/icon `<link>` tags in `<head>`).
- Google Fonts (Inter) and Material Symbols Rounded icons are loaded per-page via the same `<link>` block copied at the top of every `<head>` — replicate this block rather than inventing a new font-loading approach.
- Images/videos live in an `elements/` folder alongside the page that uses them, not in a shared media directory.
