# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A static, hand-written HTML/CSS/JS marketing site with no build system, no package manager, and no test suite. There is no `package.json`, no bundler, no framework. Every page is a plain `.html` file paired with its own `styles.css`, linked directly via `<link>`/`<script>` tags.

## Running it locally

There is no dev server or build step. Open the HTML files directly in a browser, or serve the directory with any static file server, e.g.:

```
python3 -m http.server 8000
```

Then navigate to `http://localhost:8000/index.html`.

## Site structure

The repo root is a landing page (`index.html`, `app.js`, `styles.css`) that links out to two independent sub-sites, each a self-contained mini-site with its own home/about/etc. pages:

- `HPH TECHNICAL SOLUTIONS/` — pages: `home`, `about`, `milestones`
- `HPH RENEWABLE/` — pages: `home`, `about`, `products/product-pages/content1/page1|2|3` and `content2/page1|2` (individual product pages only — there is no all-products listing page; the product lineup is reached through the nav menu), `contact`, `legal-policies` (`terms-and-conditions`, `privacy-policy`, `return-and-refund-policy`)

Each page is a directory containing `index.html` + `styles.css`, and often an `elements/` subfolder holding page-local images/videos referenced by relative path.

**JS sharing is inconsistent between the two sub-sites** — don't assume one pattern applies to both:
- `HPH RENEWABLE` has its own copy of `app.js` (`HPH RENEWABLE/app.js`) that its pages reference via `../app.js`.
- `HPH TECHNICAL SOLUTIONS` has no local `app.js`; its pages reach up to the repo-root `app.js` via `../../app.js`.

Global asset folder naming also differs between sub-sites (not a typo to "fix" without checking both):
- `HPH RENEWABLE/global-elements/` (hyphenated)
- `HPH TECHNICAL SOLUTIONS/global elements/` (space)
- repo root: `global elements/` (space)

When adding a new page inside a sub-site, match that sub-site's existing relative-path depth and JS/asset-folder convention rather than copying from the other sub-site.

## Shared front-end patterns

`app.js` (and `HPH RENEWABLE/app.js`, kept in sync manually) provides the same behavior across all pages:

- **Scroll-reveal animation**: elements with class `hidden` are observed via `IntersectionObserver`; `show` is toggled on/off as they enter/leave the viewport. The corresponding CSS (`.hidden`/`.show` in each page's `styles.css`, derived from the root `styles.css`) defines the blur/translate/opacity transition. Siblings under a `.logo` container get staggered `transition-delay` via `:nth-child` for a cascading reveal effect.
- **Image slider**: `showSlides()` / `plusSlides()` / `currentSlide()` drive a manual slideshow over elements with class `mySlides` and dot indicators with class `dot`.
- **Hamburger/dropdown menu**: `toggleMenu()` toggles a `.menu a` active state and a `header.black` class; wired up via a listener on `.menu` and the first `.dropdown` element. Note this listener setup assumes both elements exist in the DOM — pages without a `.menu`/`.dropdown` element will throw on load if `app.js` is included unmodified.

**Desktop/mobile split**: layout is done via two top-level containers per page, `<div class="desktop">...</div>` and `<div class="mobile">...</div>`, toggled by a `@media (max-width: 750px)` query in each page's `styles.css` (desktop hidden, mobile shown below that width). **The `.mobile` containers are currently empty placeholders across every page in the repo** — mobile layouts have not been built out yet. Don't assume mobile support exists when making changes; flag it if a task depends on it.

CSS uses native nested selectors (e.g. `.desktop { .content { .text-container { ... } } }` in `styles.css`) rather than a preprocessor — there is no Sass/Less build step, so this relies on browser-native CSS nesting support.

## "Schedule a Visit" form (HPH RENEWABLE, Firebase)

Every "Schedule a Visit" link on HPH RENEWABLE points to the dedicated page `HPH RENEWABLE/schedule-a-visit/` (same tab). Product pages append `?product=<name>`, which pre-ticks the matching interest (`INTEREST_BY_PRODUCT` in `visit-form.js`: MX2250 → Micro Inverter, the MSU/MAU/B units → Battery). Instead of a product, visitors pick what they're interested in with two tick-chips (`.visit-chip`, checkboxes named `interest`): Micro Inverter, Battery, or both. This is saved in the existing `product` field as "Micro Inverter", "Battery", "Micro Inverter + Battery", or "Not sure yet" when neither is ticked. The admin page labels it "Interested in", and older requests keep the product they named. The form there is one shared block (`<main class="visit-page">`, outside `.desktop`/`.mobile`, like the FAQ page) handled by `schedule-a-visit/visit-form.js` (ES module). Answers go to Firestore collection `visitRequests`; optional attachments (≤3 images/PDFs, 10 MB each) go to Cloud Storage under `visitRequests/<request id>/`. The upload field asks for the visitor's last 3 electricity bills, which are used to estimate usage for an accurate quote, and it is marked "recommended", not required. `visit-form.js` keeps its own `chosenFiles` list, so each pick adds files instead of replacing the last pick, and each file has a remove button. Files can also be dragged onto the upload box. Picked and dropped files both go through `addFiles()`, and drops elsewhere on the page are ignored so the browser doesn't navigate away. The box shows drag-and-drop wording on mouse devices and "Tap to add…" on touch devices (`@media (hover: none)`). JPEG/PNG/WebP photos over 2 MB are shrunk in the browser to a JPEG with a 2400px long edge before upload. When the browser reports no file type (e.g. HEIC on Windows), the type comes from the file extension, which keeps uploads within `/storage.rules`, and their paths are stored in the request's `attachments` field. An optional "Referral code" field (pre-filled from `?ref=<code>`) is saved upper-cased as `referralCode`; it's optional in `isValidVisitRequest` too, so a cached older form still submits. Firebase settings: `HPH RENEWABLE/firebase-config.js` (while `projectId` starts with `YOUR_`, submitting shows a call/email fallback message). The SDK loads from gstatic only on submit.

- Security rules: `/firestore.rules` and `/storage.rules` — the public may create validated requests/files only; no public reads, edits or deletes. If you add or rename a form field, update `visit-form.js` and the field list in `firestore.rules`, or every submission will be rejected; upload limits live in both `visit-form.js` and `storage.rules`.
- ES modules don't load over `file://` — test the form through a local server (`python3 -m http.server`).

## Installations / serial numbers (HPH RENEWABLE admin, Firebase)

Installations used to be kept in the "HPH Renewable Master Database" Google Sheet. They now live in Firestore and are managed on the admin page's **Installs** tab (`TABS.installs` and the "installs" section of `admin/admin.js`).
- **Collections:**
  - `installs/{id}` (staff-only) holds `clientName`, `email`, `contact`, `address`, `installDate` (YYYY-MM-DD), `capacityKwp`, `inverterSerials`, `panelSerials`, `panelCount` and `batterySerials`. It also holds `source` (`admin`/`sheet`), `sheetTimestamp`, `createdAt/By` and `updatedAt/By`. `panelCount` includes panels whose serial wasn't recorded.
  - `serials/{SN}` (staff-only, `{ type, installId }`) makes a serial unique across installs.
  - `installCounts/{installId}` (public, `{ inverters, panels }`) is what the counters add up.
  - All three are written in one batch by `saveInstall()`/`deleteInstall()`, and `isValidInstall`/`isValidSerial`/the `installCounts` match rule in `/firestore.rules` keep them consistent.
- **Serial formats:** MX2250 serials are `Y` + 15 characters and panel serials `Z` + 18. The sheet used all-zero placeholders (`Z000000000000000000`) for unrecorded panel serials: 236 of its 252 panel entries. `parseSerials()` skips these and the rules reject them as serials, so they only count toward `panelCount`.
- **Encoder role:** `inquiries@hphtechsolutions.com` (`ENCODER_EMAILS` in `admin.js`, `isEncoder()` in both rule files) signs in on the same admin page. Create its password account in the Firebase console, and never put the password in the repo.
  - **Layout:** it gets `body[data-role="encoder"]`, which hides the overview dashboard and the Feedback tab. Its top bar reads "Team Workspace", it has three tabs (Ocular Visits, Waitlist, Installs), and its home page is the "Add installation" form.
  - **Installs:** it can read every install but edit or delete only the ones it created.
  - **Visit requests and waitlist sign-ups:** it can view them, open attachments, use Edit details (including adding or removing attachments) and move stages. It can't delete them (`entryTools()` shows Delete to admins only, and the rules allow delete for `isAdmin()` only).
- **Admins:** admins can add, edit and delete any install, and have a one-time "Import from Google Sheet" button (`importFromSheet()`). The import reads the sheet's CSV, converts DD/MM/YYYY dates, and skips rows already imported (by `sheetTimestamp` + client name) and serials already recorded.
- **Form:** the add/edit form (`installForm()`) opens in the detail pane, which on phones sits at the top of the page. It checks serials live and fills the panel count from the panel serials until it's edited by hand.
- **Capacity:** capacity is never typed in. It's `panelCount × 0.65 kWp` (`PANEL_KWP`, `capacityFor()`; null with 0 panels), shown read-only in the form and saved with the install. An install that already has a capacity (e.g. from the sheet) keeps it unless its panel count changes. The import fills blank sheet capacities the same way. `fillMissingCapacities()` also fills any install with no capacity once, the first time an admin loads the page.
- **Counters:** `portfolio-counters.js` reads Firebase first, with a `getAggregateFromServer` sum over `installCounts`. It falls back to the Google Sheet while that collection is empty (before the import) or Firebase can't be reached.

## 3D model slides (MSU4000 Elite, MAU5000 Elite, B4000 Elite and B5000 Elite product pages)

`products/product-pages/content1/page3/` shows a 3D model as the carousel's 2nd slide using Google's `<model-viewer>` web component (loaded from jsDelivr in that page's `<head>`). It displays `elements/mau5000elite.glb`, a web-optimised version of the supplied `elements/mau5000elite.gltf` (19 MB, mm units, 1M triangles, no normals, near-white material): scaled to metres for AR, rotated +90° about X to stand upright (the export lies on its back, front panel facing up), simplified to ~267k triangles, normals added, material set to charcoal, Draco-compressed (~1 MB). Re-export from the source if the model changes rather than editing the .glb. The recipe, using glTF-Transform 4.5.1 with meshoptimizer and draco3dgltf, is: dedup → flatten → join → weld → simplify (meshopt, error 0.001, ~250k triangles) → normals → weld → prune. The result is put on a single node with rotation `[0.7071, 0, 0, 0.7071]` and scale 0.001. The material is double-sided with baseColor `[0.045, 0.045, 0.05, 1]`, roughness 0.5 and metallic 0.15, and the mesh is Draco (edgebreaker) compressed. Check orientation after converting, because a new export may not lie the same way. `content1/page2/` (MSU4000 Elite) does the same with `elements/msu4000elite.glb`, built the same way from `elements/msu4000elite.gltf` (~717k → ~250k triangles, ~1.06 MB). `content2/page1/` (B4000 Elite) shows `elements/b4000elite.glb` from `elements/b4000elite.gltf` (~420k → ~250k triangles, ~0.98 MB). As with the B5000, its mobile carousel dropped the `mobile-carousel-single` class. `content2/page2/` (B5000 Elite) likewise shows `elements/b5000elite.glb` from `elements/b5000elite.gltf` (~607k → ~243k triangles, ~0.95 MB); adding the 3D slide made its carousel two slides, so its mobile carousel no longer has the `mobile-carousel-single` class that hid the arrows/dots. Styles are top-level `.carousel-slide-3d` / `.mobile-carousel-slide-3d` rules in each page's `styles.css` (the "Drag to rotate" hint is a text-only pill positioned just above the page dots); the carousel's touch-swipe handler ignores drags that start on a `<model-viewer>` so they rotate the model instead.

## Simulations (HPH RENEWABLE)

The Discover mega panel has a "Simulations" column after "Youtube Videos" on every page that has the panel, and the mobile Discover menu has a matching heading under About Us. It links to `HPH RENEWABLE/simulations/how-solar-panels-work/`, an interactive page built on the Join the Waitlist page's shell (same nav, footers and styles, with one shared `<main class="sim-page">`). The second simulation, `simulations/panel-angle-and-direction/` ("Panel Angle and Direction", listed under How Solar Panels Work), uses `orientation.js` and the same page shell and styles. It has a draggable compass (with arrow keys) for the direction the panels face, a tilt slider with a side view, and a location picker (Manila, Baguio, Cebu, Davao). It estimates yearly and monthly output for the 2.6 kWp system from real sun positions, using a clear-sky model scaled to about 1,700 kWh/m² a year with monthly cloud factors and 80% performance. It searches tilt 0–60° and direction in 5° steps to find the best for each location (cached). The monthly chart uses validated colours (bars `#2a78d6`, best-possible ticks `#eb6834`, with dark-mode steps) and has a legend, hover tooltips and a table view. The third, `simulations/savings-calculator/` ("Savings Calculator", listed under Panel Angle and Direction), uses `savings.js`. Its inputs are the monthly bill, when the home uses power (daytime share 0.6/0.45/0.3), an optional battery (MAU5000 Elite 5 kWh, ₱150,000, or plus a B5000 Elite for 10 kWh, ₱250,000), the number of MX2250 kits (auto-recommended, adjustable) and the ₱/kWh rate (default ₱16). Each kit (4 panels, 2.6 kWp, ₱120,000) makes about 3,100 kWh a year, matching the FAQ's ₱49,600 a year. Only solar the home uses counts as savings, either directly or via the battery at 90% efficiency, with no net metering, as the FAQ recommends. Kits are recommended until another kit would add less than 60% of its output in usable savings. It shows monthly savings, the new bill, payback, yearly and 25-year savings, % of bill covered, the system and its starting-price cost, and a 25-year cumulative "savings minus cost" chart with a payback marker, hover crosshair and table. Keep its prices and yield in sync with the product pages, the FAQ and the waitlist's `data-price` values. The fourth, `simulations/inverter-failure/` ("Micro vs String Inverter: Failure", listed under Savings Calculator), uses `failure.js`. It shows the same 8 × 650 W panels on two systems side by side: 2 × MX2250 (panels 1–4 and 5–8) and one series string inverter. Tapping a panel cycles working, dirty (−30%) and broken cable (0 W, and an open circuit for the whole string), and the fault applies to both systems. Tapping an inverter makes it fail or fixes it. Each side has a "What your monitoring shows" card: per-panel messages for the TSUN app, and only "output low, cause unknown" for the string. A summary bar compares the two, and presets cover common faults. Each scene's SVG defs use a prefix (`micro-`/`string-`) so their gradient and filter ids don't clash. The fifth, `simulations/brownout-backup/` ("Brownout Backup Simulator", listed under Micro vs String Inverter: Failure), uses `brownout.js`. Visitors pick a battery (MSU4000 Elite, 4 kWh, 2,500 W backup limit; or MAU5000 Elite, 5.024 kWh, 3,600 W, the Plug & Play figure), 0–4 matching extension batteries, solar panels (none/4/8 × 650 W), the weather (affects solar only), the brownout's start time and length (1–48 h), and appliance quantities (the `APPLIANCES` list). The limits and the ≤10 ms switch time come from the data sheets in `product-data-sheets/`; note the product pages list "Output Power 2250W", which doesn't match. It models the brownout in 5-minute steps: the battery starts full with 90% usable and 95% efficiency each way. Solar uses a sine-shaped day calibrated to the savings calculator's 3,100 kWh a year per 4 panels, times a weather factor. A load over the limit means "Overloaded" (no backup). After the battery runs out, power returns when solar covers the load or the battery recharges to 20%. A scene shows day and night, a dead grid line, the house lights, the battery stack and a charge meter, and the appliance icons. A play button and scrubber step through time. On phones the scene and play bar stay pinned under the nav (`position: sticky` on `.bk-scene-card`) while the results and setup scroll beneath. This works because `.bk-sticky-zone` wraps the stage and the setup, and the stage is flattened with `display: contents` below 750px. How Solar Panels Work does the same for its `.sim-scene-wrap`. Results show hours covered and the fewest extra batteries needed. The chart shows usable charge with daylight and no-power bands, a playhead, a hover tooltip, click-to-seek and a table. `simulation.js` (a plain `defer` script) is a shading simulation. It shows four 650 W panels in full sun, wired either to one MX2250 micro inverter (four independent inputs) or to a string inverter (panels in series), switched with the "Inverter type" control. Tapping or clicking a panel (or pressing Enter/Space on it) cycles its shade through 0/25/50/90%, and presets set common scenarios. Readouts show total output, % of full sun, watts lost, and a comparison card with the other inverter type. The string model is deliberately simple: every panel runs at the weakest panel's level, or the weaker panels are bypassed, whichever gives more power. Bypassed and held-back panels get amber labels. The panels, shade overlays, wiring and label pills (`sizeTag()`) are generated in the script. Dot speed on each wire follows its power, and the solar-cell close-up's bulb follows total output. It respects `prefers-reduced-motion`.

## Live portfolio counters (HPH RENEWABLE)

`HPH RENEWABLE/portfolio-counters.js` (plain `defer` script) fills in the installed-count and total-capacity counters. It reads the totals from Firebase (`installCounts`, see "Installations / serial numbers" above) and falls back to the installation Google Sheet. It loads `firebase-config.js` relative to its own URL and uses a named Firebase app (`portfolio-counters`) so it doesn't clash with the admin page's app. It's loaded by `home/`, `portfolio/`, `our-advocacy/` and `admin/` (an "Installed portfolio" box under the Overview heading, with line dividers like the Home page) and finds its elements by data attributes — `data-portfolio-count="inverters|panels|inverter-capacity|solar-capacity"` (capacities also need `data-unit`), `data-portfolio-count="yearly-savings|lifetime-savings"` (installed MX2250s × `SAVINGS_PER_MX2250_YEAR`, ₱49,600, an estimate that may change, so keep it in sync with the FAQ and savings calculator), `data-portfolio-goal="inverters"` (progress toward `GOALS`, sets `--progress`), plus optional `data-portfolio-status-dot` / `-status-text` / `-error` — so any page can show them without its own copy of the logic. The per-unit ratings (2.25 kW per inverter, 0.65 kWp per panel) live at the top of that file. It requests only the serial-number columns with the gviz query `select F, H` (`COLUMNS_QUERY`), checks the returned headers, and falls back to the whole sheet if the columns have moved. It remembers the last counts in localStorage (`hph-portfolio-counts`) and shows them instantly on the next visit. It refreshes every 30 s without dimming the numbers, and on a failed refresh it keeps the last known numbers. Both pages preconnect to `docs.google.com`. Note: the sheet is readable by anyone with the link, including the client columns.

## Dark mode (HPH RENEWABLE)

Dark mode follows the visitor's system setting (`prefers-color-scheme`) on desktop and mobile. It uses the same #FFFFFF → #0C0C0C surface mapping everywhere, with #EBEBEB text, #9E9E9E muted text and #2A2A2A borders.
- **Product pages** (`products/product-pages/*`) are deliberately light only, because their photos and renders aren't made for a dark page. They have no dark rules and carry `<meta name="color-scheme" content="light">`. Don't add dark mode to them.
- **Home** has its own desktop dark block inside `.desktop`. Its landing text sits over the video and stays white.
- **Every other page** ends its `styles.css` with a `/* ===== DESKTOP DARK THEME ===== */` block for the desktop nav, mega panel and footer. Base colours there are nested deep, so these rules use `!important`, as Home's do. After it, depending on the page, comes one of the following:
  - the page's content dark tokens (sim pages, Our Advocacy, form pages, FAQ), copied out of the phone media query so they also apply on desktop. FAQ's are nested in `.faq-page` so they outweigh its desktop selectors.
  - a "Desktop page content (dark)" block (About, Mission, Contact, Portfolio, legal pages) that repeats each light content colour's selector with its dark counterpart, winning by coming later.
- When you add a coloured element to a page, add its dark counterpart too.

## Conventions to follow

- Each page's CSS lives in a `styles.css` next to its `index.html`; there is no shared/global stylesheet imported across pages beyond what's copy-pasted from the root `styles.css` patterns (`.hidden`/`.show`, desktop/mobile toggle, font/icon `<link>` tags in `<head>`).
- Google Fonts (Inter) and Material Symbols Rounded icons are loaded per-page via the same `<link>` block copied at the top of every `<head>` — replicate this block rather than inventing a new font-loading approach.
- Images/videos live in an `elements/` folder alongside the page that uses them, not in a shared media directory.
