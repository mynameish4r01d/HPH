# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A static, hand-written HTML/CSS/JS marketing site with no build system, no package manager, and no test suite. There is no `package.json`, no bundler, no framework. Every page is a plain `.html` file paired with its own `styles.css`, linked directly via `<link>`/`<script>` tags.

## Running it locally

There is no dev server or build step. Open the HTML files directly in a browser, or serve the directory with any static file server, e.g.:

```
python3 -m http.server 8000
```

Then navigate to `http://localhost:8000/index.html`.

## Site structure

The repo root is a landing page (`index.html`, `app.js`, `styles.css`) that links out to two independent sub-sites, each a self-contained mini-site with its own home/about/etc. pages:

- `HPH TECHNICAL SOLUTIONS/` — pages: `home`, `about`, `milestones`
- `HPH RENEWABLE/` — pages: `home`, `about`, `products/product-pages/content1/page1|2|3` and `content2/page1|2` (individual product pages only — there is no all-products listing page; the product lineup is reached through the nav menu), `contact`, `legal-policies` (`terms-and-conditions`, `privacy-policy`, `return-and-refund-policy`)

Each page is a directory containing `index.html` + `styles.css`, and often an `elements/` subfolder holding page-local images/videos referenced by relative path.

**JS sharing is inconsistent between the two sub-sites** — don't assume one pattern applies to both:
- `HPH RENEWABLE` has its own copy of `app.js` (`HPH RENEWABLE/app.js`) that its pages reference via `../app.js`.
- `HPH TECHNICAL SOLUTIONS` has no local `app.js`; its pages reach up to the repo-root `app.js` via `../../app.js`.

Global asset folder naming also differs between sub-sites (not a typo to "fix" without checking both):
- `HPH RENEWABLE/global-elements/` (hyphenated)
- `HPH TECHNICAL SOLUTIONS/global elements/` (space)
- repo root: `global elements/` (space)

When adding a new page inside a sub-site, match that sub-site's existing relative-path depth and JS/asset-folder convention rather than copying from the other sub-site.

## Shared front-end patterns

`app.js` (and `HPH RENEWABLE/app.js`, kept in sync manually) provides the same behavior across all pages:

- **Scroll-reveal animation**: elements with class `hidden` are observed via `IntersectionObserver`; `show` is toggled on/off as they enter/leave the viewport. The corresponding CSS (`.hidden`/`.show` in each page's `styles.css`, derived from the root `styles.css`) defines the blur/translate/opacity transition. Siblings under a `.logo` container get staggered `transition-delay` via `:nth-child` for a cascading reveal effect.
- **Image slider**: `showSlides()` / `plusSlides()` / `currentSlide()` drive a manual slideshow over elements with class `mySlides` and dot indicators with class `dot`.
- **Hamburger/dropdown menu**: `toggleMenu()` toggles a `.menu a` active state and a `header.black` class; wired up via a listener on `.menu` and the first `.dropdown` element. Note this listener setup assumes both elements exist in the DOM — pages without a `.menu`/`.dropdown` element will throw on load if `app.js` is included unmodified.

**Desktop/mobile split**: layout is done via two top-level containers per page, `<div class="desktop">...</div>` and `<div class="mobile">...</div>`, toggled by a `@media (max-width: 750px)` query in each page's `styles.css` (desktop hidden, mobile shown below that width). **The `.mobile` containers are currently empty placeholders across every page in the repo** — mobile layouts have not been built out yet. Don't assume mobile support exists when making changes; flag it if a task depends on it.

CSS uses native nested selectors (e.g. `.desktop { .content { .text-container { ... } } }` in `styles.css`) rather than a preprocessor — there is no Sass/Less build step, so this relies on browser-native CSS nesting support.

## "Schedule a Visit" form (HPH RENEWABLE, Firebase)

Every "Schedule a Visit" link on HPH RENEWABLE points to the dedicated page `HPH RENEWABLE/schedule-a-visit/` (same tab). Product pages append `?product=<name>`, which pre-ticks the matching interest (`INTEREST_BY_PRODUCT` in `visit-form.js`: MX2250 → Micro Inverter, the MSU/MAU/B units → Battery). Instead of a product, visitors pick what they're interested in with two tick-chips (`.visit-chip`, checkboxes named `interest`): Micro Inverter, Battery, or both. This is saved in the existing `product` field as "Micro Inverter", "Battery", "Micro Inverter + Battery", or "Not sure yet" when neither is ticked. The admin page labels it "Interested in", and older requests keep the product they named. The form there is one shared block (`<main class="visit-page">`, outside `.desktop`/`.mobile`, like the FAQ page) handled by `schedule-a-visit/visit-form.js` (ES module). Answers go to Firestore collection `visitRequests`; optional attachments (≤3 images/PDFs, 10 MB each) go to Cloud Storage under `visitRequests/<request id>/`. The upload field asks for the visitor's latest electricity bill (with the "Your Monthly Consumption" graph visible), which is used to estimate usage for an accurate quote, and it is marked "recommended", not required. It still accepts up to 3 files, in case the bill has several pages. `visit-form.js` keeps its own `chosenFiles` list, so each pick adds files instead of replacing the last pick, and each file has a remove button. Files can also be dragged onto the upload box. Picked and dropped files both go through `addFiles()`, and drops elsewhere on the page are ignored so the browser doesn't navigate away. The box shows drag-and-drop wording on mouse devices and "Tap to add…" on touch devices (`@media (hover: none)`). JPEG/PNG/WebP photos over 2 MB are shrunk in the browser to a JPEG with a 2400px long edge before upload. When the browser reports no file type (e.g. HEIC on Windows), the type comes from the file extension, which keeps uploads within `/storage.rules`, and their paths are stored in the request's `attachments` field. An optional "Referral code" field (pre-filled from `?ref=<code>`) is saved upper-cased as `referralCode`; it's optional in `isValidVisitRequest` too, so a cached older form still submits. Firebase settings: `HPH RENEWABLE/firebase-config.js` (while `projectId` starts with `YOUR_`, submitting shows a call/email fallback message). The SDK loads from gstatic only on submit.

- Security rules: `/firestore.rules` and `/storage.rules` — the public may create validated requests/files only; no public reads, edits or deletes. If you add or rename a form field, update `visit-form.js` and the field list in `firestore.rules`, or every submission will be rejected; upload limits live in both `visit-form.js` and `storage.rules`.
- ES modules don't load over `file://` — test the form through a local server (`python3 -m http.server`).

## Installer checklists (HPH RENEWABLE admin, Firebase)

The admin page has an **installer account** (`INSTALLER_EMAILS` in `admin/admin.js`: `hphrenewable@gmail.com`; `isInstaller()` in both rule files, so keep the three in step). It signs in on the same admin page, either with email + password (create the account in the Firebase console, never put the password in the repo) or "Sign in with Google". Its workspace ("Installer Checklists", `body[data-role="installer"]`) has no overview and only three tabs: **Site visit inspection** (`inspection`), **Installation and commissioning** (`installation`) and **Inventory** (see "Inventory" below). Admins see the same two tabs, shortened to Inspection and Commissioning, plus an "Installer checklists" box on the overview. The encoder account sees neither.
- **Content:** `admin/checklist-templates.js` holds every item and is the owner’s real list (Site Visit: 7 items; Installation: 9; the installer sees the tabs as "Site Visit" and "Installation"). Item ids are the keys answers are saved under, so don’t rename one that has answers. Bump `CHECKLIST_VERSION` when the content changes. A `sample: true` flag on a checklist would show a "Sample content" tag. Three item kinds, all resolved by `itemResult()` in `admin.js` (so counters, report, CSV and form agree, and the rules need no change): a normal item is Pass / Needs fix / N/A (`r`); `options: [...]` is a question with set answers (chosen one saved as `v`, answers in `flagged` count as Needs fix, e.g. Wi-Fi Bad / Needs improvement); `type: "photo"` is answered by a photo (pass) or N/A, and `notePrompt`/`noteRequired` show a note box that must be filled before it counts as answered (the cable-length estimate).
- **Flow:** "Start a checklist" (or the pane's home, for the installer) opens a picker of clients from the Ocular Visits list (by default those at the matching stage: inspection = New to Visited, installation = Quote sent and Installing; searching or "Show all clients" shows the rest) or a job typed by name and address. Each item is answered Pass / Needs fix / N/A, with an optional note (opens automatically on Needs fix) and photos (up to 6, JPEG-shrunk like the other uploads, `jobChecklists/<id>/` in Storage). It saves as you go (notes after a 700ms pause, and `flushChecklist` saves anything pending before a refresh). Submitting needs every item answered and a name, and locks it; an admin can **Reopen** it. Only the creator can edit a checklist (admins can read, reopen and delete).
- **Data:** Firestore `jobChecklists/{type}-{visit request id}` (or an automatic id for a typed job): `type`, `visitId`, `clientName`, `address`, `items` (map of item id to `{ r, note, photos }`), counters `total/answered/passed/fixes/na` (kept in step by every save, so the overview needn't read answers), `status` (`in_progress`/`submitted`), `version`, `signedOffBy`, `submittedAt`, `createdAt/By`, `updatedAt/By`. Rules: `isValidChecklistCreate/Update/Reopen` in `/firestore.rules` (the counters must add up, the job's details can't change, submitting needs `answered == total`), and a `jobChecklists/` rule in `/storage.rules`. The installer can also read visit requests (to pick a client) but change nothing, so it sees client names, phones and addresses.
- **Import from Ocular Visit:** a photo item with `fromVisit: true` (the Site Visit's "Latest Meralco bill uploaded") also has an "Import from Ocular Visit (n)" button. It shows when the checklist was started from a visit request that has attachments.
  - **Linking:** it links every attachment of that request to the item, up to the item's 6 files. These are the request's own `visitRequests/<id>/…` paths, not copies.
  - **Display:** PDFs show as a tile that opens the file, and linked files carry a "From visit" tag.
  - **Removing:** removing one only unlinks it. `checklistPhotoPaths()` leaves linked files out, so deleting a checklist never deletes them.
  - **Deleted requests:** if an admin deletes the visit request, its files go too.
  - **Storage rule:** the installer may view (`get`) visit-request files, but not delete them.
- **Admin overview:** `renderChecklistOverview()` shows in-progress and submitted counts, items needing a fix, last activity, an alert for jobs in Installing with no installation checklist, and a row per job with each checklist's progress (click to open it). Export CSV works on both tabs (`CHECKLIST_CSV`).
- **Testing:** the rules were checked against the Firebase Firestore emulator (61 requests as installer, admin, encoder and strangers; also covers the NDA rule). The interface was checked by driving the real page in headless Chrome with an in-memory stand-in for the Firebase SDK served in place of the gstatic modules (installer on a phone and desktop, admin on a desktop).

## Inventory (HPH RENEWABLE admin, Firebase)

The installer workspace, the team workspace (encoder) and admins have an **Inventory** tab (`TABS.inventory` and the "inventory" section of `admin/admin.js`; `canKeepInventory()` in `/firestore.rules`, and the `inventory/` rule in `/storage.rules`). On that tab the installer's and encoder's home is "Stock on hand".
- **Items:** `inventory/{id}` holds `name`, `category`, `unit`, `qty`, `lowAt` (restock level, 0 = warn only when none are left), `note`, `photos` (up to `INV_MAX_PHOTOS`, 6, shrunk like other uploads, in Storage under `inventory/<id>/`), `lastLogId` and `createdAt/By`, `updatedAt/By`. Category and unit are dropdowns. The categories (`INV_CATEGORIES`) are Cables & Wiring, Connectors, Major Equipment, Mounting & Racking and Grounding Hardware, and a category is required. The units (`INV_UNITS`) are pcs and mtrs. An older value not in the list stays selectable. An item is "Restock" (amber) at or below `lowAt` and "Out of stock" (red) at 0. The list sorts those first, and the sidebar's "Restock needed (n)" button filters to them. A category dropdown beside the search box filters by category (`.admin-category-filter`, `renderCategoryFilter()`, `activeCategory`). It lists All categories, the `INV_CATEGORIES`, any older category still in use and "No category" if any, each with a count. It combines with search and the restock filter, and Export CSV follows it. With All categories, the list is grouped by category (`groupedInventory()`), in the dropdown's order. Each group has a heading with its count and "n to restock", and the heading stays pinned while scrolling on desktop. Within a group the order is out of stock, then low, then by name.
- **Changing the count:** each item has a stock panel: Use / Add stock / Set count, a −/+ stepper, a preview of the new count, "Used for" (client suggestions from Ocular Visits) and a note.
  - **Saving:** there's no save button. A change saves `PANEL_SAVE_MS` (1.5 s) after the last tap, with "Saving in a moment… Cancel" shown meanwhile.
  - **Text fields:** it waits while Used for / Note is being typed in, and saves when the field is left or Enter is pressed.
  - **Starting values:** Use and Add stock start at 0, so nothing saves until an amount is picked. Set count starts at the current count.
  - **Mode:** switching mode drops an unsaved change, and the mode is remembered per item (`panelModes`).

  `changeStock()` runs a transaction that updates the item and writes an `inventoryLog/{id}` record (`itemId`, `itemName`, `reason` create|use|restock|count, `change`, `qtyBefore`, `qtyAfter`, `job`, `note`, `at`, `by`), shown as the item's History. Each list row also has a quick − count + (`quickStepper()`). Taps are added up and saved as one Used / Stock added change `QUICK_SAVE_MS` (1.5 s) after the last tap (`saveQuick()`, same transaction and rules). The count shows blue until saved, and leaving the page saves what's waiting and asks to confirm. The add/edit form (`showItemForm()`/`itemForm()`) changes details and photos only; a new item's starting count is written with a "create" record.
- **Rules:** `isValidInventoryItem`, `isInventoryLogFor` and `isValidInventoryLog` in `/firestore.rules`. A count change must come with a new record for that item whose before/after match, and records can't be edited (admins may delete them). The installer and admins read and write. Admins delete any item, the installer and encoder only their own. Photos use the `inventory/` rule in `/storage.rules`. The history query filters by `itemId` only and sorts in the browser, so it needs no composite index.
- **Admin overview:** an Inventory box (`renderInventoryOverview()`) shows the same summary (`inventorySummary()`), and a restock row opens that item on the Inventory tab.
- **Installer home:** on the Inventory tab the installer's pane is "Stock on hand" (`showInventoryHome()`; also admins' on desktop when no item is open, `inventoryHomeShown()`): item, running-low and out-of-stock tiles and the restock list. "Add item" is only in the sidebar, next to "Restock needed".
- **Testing:** the rules were checked against the Firestore emulator (38 requests: create, read, Use / Add stock / Set count including stale counts, replays and missing records, edits, deletes; installer, admin, encoder, stranger).

- **Matching:** each visit request stores its OpenSolar project ids (`openSolarIds`). A project already listed updates that entry; new entries get the ID `opensolar-<first project id>`.
  - **First link:** the first time, each client is scored against entries not yet linked (`clientScore()`/`clientCandidates()`). Same phone +3. The chart shows usable charge with daylight and no-power bands, a playhead, a hover tooltip, click-to-seek and a table. `simulation.js` (a plain `defer` script) is a shading simulation. It shows four 650 W panels in full sun, wired either to one MX2250 micro inverter (four independent inputs) or to a string inverter (panels in series), switched with the "Inverter type" control. Tapping or clicking a panel (or pressing Enter/Space on it) cycles its shade through 0/25/50/90%, and presets set common scenarios. Readouts show total output, % of full sun, watts lost, and a comparison card with the other inverter type. The string model is deliberately simple: every panel in the series string runs at the weakest panel's level (no bypassing), so one shaded panel pulls the whole system down, while on the micro inverter shade stays isolated to that panel. Held-back panels get an amber watts pill under the panel and an amber two-line "Held back / by panel N" tag on the panel face (the slot shaded panels use for their two-line shade tag, via `setLines()`), so neighbouring labels never overlap. `failure.js` uses the same weakest-link model for a dirty panel (the other string panels are tagged "Held back"). In both, the string side is drawn as a true series chain: a jumper under the panels links each panel to the next (`jump<i>` flows), and a single lead runs from the last panel to the string inverter. Dots on the jumpers slow step by step as they approach the weakest panel (`jumperWatts()`, over `APPROACH` jumpers), then stay at its reduced speed for the rest of the string; this is illustrative, since real series current is the same everywhere. `failure.js` scales string dot speed to the string's full output so a weaker string visibly slows, and each panel there shows its own watts in a small pill on its face (`fail-watt-tag`, amber below 650 W); its monitoring messages give watts too. The panels, shade overlays, wiring and label pills (`sizeTag()`) are generated in the script. Dot speed on each wire follows its power, and the solar-cell close-up's bulb follows total output. It respects `prefers-reduced-motion`.

## Dark mode (HPH RENEWABLE)

Dark mode follows the visitor's system setting (`prefers-color-scheme`) on desktop and mobile. It uses the same #FFFFFF → #0C0C0C surface mapping everywhere, with #EBEBEB text, #9E9E9E muted text and #2A2A2A borders.
- **Product pages** (`products/product-pages/*`): the MX2250 page (`content1/page1`) is deliberately light only, because its photos aren't made for a dark page. It has no dark rules and carries `<meta name="color-scheme" content="light">`. The MSU4000 Elite, MAU5000 Elite, B4000 Elite and B5000 Elite pages have dark mode, at the owner's request (`content="light dark"`). Their dark rules are at the end of each `styles.css`: nav, page content, mobile tokens, the 3D slide's dark grey stage (#1C1C1E), dots, arrows, controls, labels, tour card, and (MSU/MAU) the steppers, total capsule and price line. The photo slides keep their light stage, because the charcoal products disappear on a dark background.
- **Home** has its own desktop dark block inside `.desktop`. Its landing text sits over the video and stays white.
- **Every other page** ends its `styles.css` with a `/* ===== DESKTOP DARK THEME ===== */` block for the desktop nav, mega panel and footer. Base colours there are nested deep, so these rules use `!important`, as Home's do. After it, depending on the page, comes one of the following:
  - the page's content dark tokens (sim pages, Our Advocacy, form pages, FAQ), copied out of the phone media query so they also apply on desktop. FAQ's are nested in `.faq-page` so they outweigh its desktop selectors.
  - a "Desktop page content (dark)" block (About, Mission, Contact, Portfolio, legal pages) that repeats each light content colour's selector with its dark counterpart, winning by coming later.
- When you add a coloured element to a page, add its dark counterpart too.

## Conventions to follow

- Each page's CSS lives in a `styles.css` next to its `index.html`; there is no shared/global stylesheet imported across pages beyond what's copy-pasted from the root `styles.css` patterns (`.hidden`/`.show`, desktop/mobile toggle, font/icon `<link>` tags in `<head>`).
- Google Fonts (Inter) and Material Symbols Rounded icons are loaded per-page via the same `<link>` block copied at the top of every `<head>` — replicate this block rather than inventing a new font-loading approach.
- Images/videos live in an `elements/` folder alongside the page that uses them, not in a shared media directory.
